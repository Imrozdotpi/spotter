## 1. e1RM formula vs the RTS RPE chart

The chart gives the percentage of a one-rep max that a set of *reps* at a given *RPE* represents. Spotter's formula implies its own percentage: `100 / (1 + (reps + RIR) / 30)` with `RIR = 10 − RPE`, and exactly 100 when `reps + RIR = 1`. This section compares the two. It is a comparison, not a pass/fail test: the two were never meant to match exactly.

Chart values were supplied in the build brief. They have not been independently checked against the original source.

**What this shows**

- Over all 80 cells, Spotter's formula is off by 1.15 points on average. Plain Epley, which cannot see RPE, is off by 4.77 points. Adding RPE removes 75.8% of the error.
- The worst cell is 10 reps at RPE 6.5: chart 64%, Spotter 69.0% (+5.0 points).
- In kilograms: for a lifter whose true max is 100 kg according to the chart, that worst-case set would give a Spotter e1RM of 92.8 kg, which is 7.2 kg off. At 4–6 reps the same calculation is within about 1 kg.
- The error is not random: see the signed column. Where it is consistently positive or negative, Spotter's e1RM is consistently below or above the chart's. For readiness this matters less than it looks, because Spotter compares your e1RM with *your own* earlier e1RMs from the same formula. A constant bias cancels. A bias that changes with reps does not, so a day where you do far fewer or far more reps than usual is compared less fairly.
- Plain Epley at RPE 10 is, by construction, identical to Spotter's formula (checked in the unit tests for reps 1–12).

## 6. Issues found in the existing tracker

Found while reading `mobile-gym.html` (now `index.html`). "Evidence" quotes the code as it is in the file today; each quote is checked to be present when this report is generated.

### 6.1 Calories-burned formula is not evidence-based

- **Evidence:** `const burned = Math.round(mins * 5.5 + done * 4);` in `updateSummaryStrip()`. When no minutes are logged it also invents them: `Math.round(done * 2.5)`. PASS
- **Decision:** **Pending (Imroz).** Not changed, as instructed. Spotter never uses this number. Options are in DECISIONS.md: hide it, relabel it "rough estimate", or replace it with a MET-based estimate that needs bodyweight.

### 6.2 RPE is pre-filled on every new set

- **Evidence:** `rpe: item.p` in `createDayObject`, `rpe: prev.rpe` in `addSet`, `rpe: s.rpe || ex.targetRpe` in `copyGhostSets`, and `rpe: "8.5"` in `confirmAddExercise`. PASS
- **Decision:** **Decided and built.** Sets carry `rpeConfirmed` (true only after the PE box is edited or the one-tap confirm is used). Unconfirmed and legacy RPEs still give a verdict, labelled low confidence. "Why?" shows how many past sessions had a typed RPE.

### 6.3 Reps are auto-filled when a set is ticked (not in the brief)

- **Evidence:** `if (m) {` → `s.reps = m[0];` in `toggleDone`: empty reps become the low end of the target range. PASS
- **Decision:** **Decided and built (agreed in Phase 0).** The set is marked `repsAutoFilled` and readiness is labelled low confidence until the reps box is edited.

### 6.4 Epley-style estimates are weak at very low and very high reps

- **Evidence:** Section 1 of this report: the error against the RPE chart is 1.03 points for 1–3 reps, 0.39 for 4–6 and 1.82 for 7–10. The chart stops at 10 reps, so nothing here validates 11–12 reps or higher. PASS
- **Decision:** **Decided and built.** Only sets with 1–12 reps and RPE 6–10 are used; others are skipped with the reason shown. Like-for-like comparison (first working set against earlier first working sets) limits the effect. The cut-offs are in DECISIONS.md.

### 6.5 Renaming an exercise breaks its history

- **Evidence:** History is matched by name only: `e.name.toLowerCase() === exName.toLowerCase()` in `getGhostBest`. Names are free text (`editExName`). There is no exercise id. PASS
- **Decision:** **Partly addressed, rest pending (Imroz).** Spotter matches on a normalised name (trim, lowercase, single spaces), so spacing and capitals no longer split a history. A real rename still starts a new trend. A stable id per exercise would fix it but changes the data model, so it is only proposed in DECISIONS.md.

### 6.6 User text is put into `innerHTML` without escaping (XSS risk)

- **Evidence:** `value="${ex.name}"` in `renderWorkout`, `<strong>${f.name}</strong>` in `renderNutrition`, `<strong>${name}</strong>` in `renderStatsView`. A name containing `"` or `<` breaks the markup; a crafted backup file could run script. PASS
- **Decision:** **New code is safe; old code pending (Imroz).** Everything Spotter renders goes through `escapeHtml` (tested). The three existing spots are unchanged, as instructed. The proposed fix is three one-line edits, listed in DECISIONS.md. The risk today is low because the only text is your own typing and your own backup files.

### 6.7 A failed save is silent (not in the brief)

- **Evidence:** `SafeStore.set` catches the error and keeps the value in memory only: `this.mem[key] = val;`. After a reload that data is gone. PASS
- **Decision:** **Mitigated.** `SafeStore` is unchanged, but Spotter reads back every write and shows a red warning in the header if it did not stick.

### 6.8 Changing the split discards the day's exercises without asking (not in the brief)

- **Evidence:** `const fresh = createDayObject(splitKey);` in `changeDaySplit` replaces the exercises and logged sets for that day. PASS
- **Decision:** **Pending (Imroz).** Existing behaviour, unchanged. Spotter's new fields are carried across. A confirm step is proposed in DECISIONS.md.
